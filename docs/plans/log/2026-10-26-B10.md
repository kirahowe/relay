# B10: the daily note

The morning brief is gone. `relay.brief`, its test, `render/brief`,
`dispatch/send-brief!`, `:brief/send` and the `:brief` setting were
deleted. relay.edn now refuses `:brief` and points to `:daily-note
{:at "07:30" :role "steward"}`. An old `brief/composed` event still
folds, and counts as that day's note (I8).

What was built:

- `relay.digest` (pure): when the note is due, which changes it flags,
  how it words each one, the note itself, and what a reply asks for.
  `:digest/compose` in `relay.core` makes the note from the log alone;
  the tick submits it when it is due (`dispatch/send-daily-note!`). The
  message is a `digest` with origin `daily-note`, and it keeps
  `:numbered`, the meaning of each number in it.
- Changes to how a role works. Whenever relay folds an event that
  writes a skill (a doc under `skills/<role>/`), a routine, a note or a
  role, it records a change (`:recipe-changes`) together with what that
  change replaced. The flagged section lists every change since the
  last note that a role (not the operator) made while its session
  carried outside provenance (`contaminated` or a `kind:what` source
  label). Each entry has one line saying what changed, the source in
  plain words and `relay revert <n>` / reply "revert N". The model
  never writes this section, and nothing it writes can remove an entry
  (a property in `digest_test`, and one in `daily_note_test` over
  sequences of real commands). Past 40 entries the note counts the
  rest; `relay changes` lists them all.
- Revert: `:change/revert` (the CLI's `relay revert <ref>`) and
  `:digest/act` (`_relay/messages/act`, `relay dismiss`, a reply). It
  puts back the version before the change, or removes what the change
  made. Restored text keeps its own labels, and since the operator does
  the revert, the revert is never flagged.
- The parts a steward writes: `daily_note_draft` (read) and
  `daily_note_write` (edit), offered only to the role `:daily-note`
  names. The parts are `ahead`, `grants`, `github` and `learned`. Any
  suggestion the operator turned down is dropped when the role writes
  it, and again when the note is made. `bb staging init` gives the hub
  `:daily-note`, a `daily-note` routine at 07:10 and a skill,
  `skills/hub/daily-note.md`.
- Dismissal: `suggestion/dismissed` records the keys of the suggestion
  (the key the role gave and one made from its text), with its text and
  labels. `daily_note_draft` shows the role what was turned down.
- Replies: a verified reply to the note (B8's path) that says "revert
  1", "undo 1 and 3", "not 2", "dismiss 2, 4", or just "not this one"
  when the note has exactly one suggestion, is acted on in code. relay
  answers in the thread with what it did, and the role still reads the
  reply as a memo. An unverified reply changes nothing.
- GitHub: `github-items` keeps `user.type`. A new item opened by a
  person (type `User`, login not ending `[bot]`) goes onto
  `:github-news`, and the tick sends one message for all of them after
  polling (`:github/announce`); `relay poll` does too.
- Client: `_relay/messages/act {"message", "item"}`. An item the note
  numbers carries `action` `{op, n, done}` in its wire form.

Judgment calls, conservative where the brief was silent:

- The setting is its own key, `:daily-note {:at :role}`, rather than
  reusing `:messages :digest-at`. That time is when held low-urgency
  deliveries go out, which is a different thing.
- Undoing restores what was there just before the flagged change, even
  when later changes followed it. Those later changes may build on the
  outside text. Undoing is itself a new version, and nothing is lost.
  When the version it would restore was itself written by a change that
  was undone too, the undo goes back past that one (fix round 1: undoing
  two mail-shaped changes to one skill oldest first used to leave the
  second one's text in place).
- A role that was removed cannot be brought back: ids are never reused,
  and removing it also stopped its routines and dead-lettered its
  memos. Its removal is flagged, but undoing it is refused with a plain
  reason.
- The flagged section covers changes made by roles only. What the
  operator writes is theirs, including a revert that restores outside
  text.
- The first note, with no note before it, looks back one day, so a log
  full of history does not flag every past change at once.
- A reply's "not this one" is acted on only when the note has a single
  suggestion. Otherwise it is left for the role to read.
- Numbered items: flagged changes and suggestions in `ahead` and
  `grants`. `github` and `learned` are not numbered.
- Flagged entries name the thing by its restricted identifier (a skill's
  slug, a routine or note name, a role id) and never quote its text.
  That name can still be the outside text's choice (a skill path may
  hold dots and slashes), so when the change was shaped by outside text
  the name is defanged everywhere relay shows it: the note, relay's
  answer to a reply, and `relay changes` (fix round 1). The item itself
  carries no labels: the line is relay's own words and already names
  the source, so marking the whole line as outside text would repeat it.
- GitHub items opened by the operator's own account count as a
  person's, since relay.edn has no setting for the operator's GitHub
  login.

## Fix round 1

- Undo order: each recorded change now keeps `:prior`, the change before
  it to the same thing. An undo walks back through priors the operator
  has undone too and restores the version before all of them. Property:
  trusted writes, then outside-shaped writes, then every outside change
  undone in a random order, leaves skills, notes and routines exactly as
  the trusted writes left them, labels included. Restoring a skill now
  also rewrites it when only its labels differ.
- Outside-chosen names are defanged (see above).
- Tests now check the labels of what an undo restores (skill, routine,
  note, role) and the labels of a part the steward wrote from outside,
  through the note, the client's outsider mark, the mail text and
  `daily_note_draft`. The reviewer's mutants M3, M4, M10 and M14 each
  fail a test now.
