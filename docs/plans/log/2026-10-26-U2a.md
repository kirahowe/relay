# U2a: the final UX panel's relay findings

## The command line

- `relay routine run` printed a stack trace after the wake had run: it
  called `render/wake-result` without the role. Fixed, with a test of
  the output.
- `relay status` (and the tick's alert) lists every problem in
  relay.edn at once, numbered, each with its fix, and every settings
  refusal exits 1. `config/validate` collects through `problem!`; a step
  that crashes on input an earlier problem broke counts only when
  nothing else was found, and is then thrown as it is (tested in fix
  round 1, so a crash can never let relay.edn through). A removed key is told once, not also as an
  unknown one. A property injects any mix of nine independent old-file
  mistakes and checks each is named.
- The old web tool's refusal gives its fix: add `:queries ["query"]`.
- A removed command (holds, approve, deny, release, trust, review,
  verify, ledger, trust-level, brief) says what replaced it in one line.
- `relay memo steward` on a relay whose main role is hub names hub;
  `relay help` names the main role from relay.edn when it can read it.
  The shell's status line names the role granted the shell.
- `relay help` lists note, accept, decline and routine run. Per-command
  help for init, memo and reply says more (options and an example).
- `relay status` wraps at 60 columns with each command on its own
  line; says when the tick has never run or has not run for 20 minutes
  (the tick writes `<data>/.last-tick` at most every five minutes, and
  nothing while paused); says when a mailbox has no `:authserv-id`; in
  a directory with only relay.edn it says role names are checked later
  instead of suggesting init (fix round 1: "no log" now means no log
  directory, not no relay.edn); earlier weeks of spend start at the week
  of the log's first event in the operator's zone, and an empty log has
  none; and an `:ingest` source whose `:to` names no role is
  named (it is in `role-name-problems`, so the tick alerts too).
- `relay tick` says whom it woke; by hand in a terminal it says when
  nobody had anything to do.
- `relay poll` says what came in: events by name, `#44 by lee-m`, mail
  subjects, defanged.
- `relay calendar url` gives http for 127.0.0.1, then probes the feed
  once and says when relay serve is not running, something else holds
  the port, or the tailnet address is not published (with the
  `tailscale serve` line).
- `relay changes` before any note: "To undo one: relay revert c<k>,
  such as relay revert c7."

## The daily note

- "yes N", `relay accept N` and `_relay/messages/act` op accept take up
  an offer: an `offer/accepted` event and a memo from the operator to the
  note's writer ("Yes: <offer>") that wakes it.
- The note's text holds no channel's wording. `digest/with-hints` adds
  how to act per medium: reply words in mail when relay reads replies
  (`ingest/reads-replies?`: a pop3 source with `:authserv-id`), commands
  at the command line (`relay note`, `relay ready <n>`), nothing in a
  push or the client.
- A refusal names the command at the command line, plain words in the
  client, a reply word in a reply. Done-ness is checked first ("Item 3
  was dropped already."). An item of Coming up is "something coming up",
  and dropping one says it will not be in later notes.
- An answer to a reply that did everything it asked is resolved (in the
  thread, not a new Ready item); one with a refusal stays. `relay reply`
  to the note prints the answer and exits 1 on a refusal.
- The peek quotes a line of words, not code (no ``` blocks, backticks or
  shell prompts) when the change has one.
- The note waits up to an hour past its time while its writer works or
  has memos open. Coming up with nothing written says "I haven't gone
  through your calendar yet today." A note made before the writer wrote
  Coming up can be made again with `relay note now` once it has
  (`digest/composed` records `:parts`).

## Messages

- Old notification events fold as history: resolved, `:legacy`, not in
  Ready, and a reply to one is refused.
- When a role closes the operator's own memo, the outcome reaches her as
  a low-urgency reply ("Re: <subject>", origin request-done), routed like
  any message, unless the role told her about that memo itself, the
  memo was her reply to a message, or the closer is public.
  resources/AGENTS.md and the wake prompt's header on her memo tell
  roles the outcome is what she reads.
- A dead letter is not told to her when the role told her about that
  memo itself.
- (Fix round 1.) "Told her about that memo" means a tell_operator call
  that passed `memo` (recorded as the message's `:request`). The first
  version suppressed on any tell in the same wake, which lost her second
  request's outcome and, worse, the alert for a failed request after an
  unrelated "FYI" (the model property caught it on some seeds). The
  handler's dead-letter memo says "relay has told the operator" only
  when relay did, and "<role> has told the operator" when the role did.
- Ready shows list items behind "- ", and hidden characters as mail
  does ("(a hidden character removed)"), never escaped twice.
- An outside tool whose labels say only contaminated is named as a
  source (`tool:cal`, "the cal tool"), not "something from outside".
- `:calendar {:name ...}` names the agent's calendar; without it, the
  email channel's `:from-name`, else Agenda.

## Setup

`relay init` writes the relay-tui built next to relay (else PATH's) as an
absolute `:client`. A missing relay-tui says how to build it. README
Setup builds agentloop, relay-tui and webtool and installs relay.serve.
README says new GitHub items wait for the note when there is one.
DEPLOY.md: every command uses `bin/relay --data <live data>`, `:house`
mounts the notes folder as trusted with the mount rule stated plainly,
the table has rows for the old web tool and a contaminated `cal` tool,
and step 1 says every problem is listed.

## Evals

Two graders follow the behaviour: mail-shaped-change-flagged checks the
note numbers the change (the "revert N" words are per channel now), and
no-needless-notify allows relay's own quiet answer to the request.

Fix round 1: a new case, operator-question-answered, from the staging
exchange where the steward closed a request with "Told you what I know
about you below." and put the answer only in its final text. Its foil
does exactly that. The concert email's oracle and foils pass `memo` to
tell_operator. Without the prompt line naming `memo`, Haiku told her
twice on the concert email (3 of 3); with it, 3 of 3 passed. Run ids
are in BASELINES.md.

Not done: a structural backstop that copies a wake's final text into
the request's reply. The final text is the model talking to itself
("Done. Closed memo 12, wrote my journal."), so it would put internals
in front of her; the prompt line and the eval stand instead. Left for
Kira below.
