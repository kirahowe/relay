# B9: organizing files

Added `files_move` (class `edit`, ACP kind `move`) for a house role
granted `:files`, a vector of folders it may organize. relay's own code
makes the moves on the host, in `relay.files` (decisions and disk steps)
and `relay.moves` (a call under the data directory's files lock).
`relay moves` lists the calls, and `relay undo <move>` puts one back.
Closes relay#53.

Each call is two events: `files/moving` before anything moves, with the
real paths asked for, and `files/moved` after, with each step's index, a
fingerprint (size and SHA-256, every entry of a folder) and the folders
it made. `files/undone` records what undo put back and which folders it
removed. All three carry private and the labels of the session or call
they come from.

Judgment calls:

- The writable folders are a per-role grant, `:grants {"steward"
  {:files [...]}}`, because Kira decided on relay#53 that folder access
  is granted per role. They are separate from `:house :mounts`, and a
  folder may be in both. relay does not mount them in the shell on its
  own, since the shell's mounts are global and the grant is per role.
- The folder checks reuse the shell's: `shell/place-problem` (split out
  of `mount-problem`, which keeps its behaviour) on the path as written
  at load, and `place-problem` with `identity-problem` on the real path
  when a call runs. A folder that is a link to the data directory passes
  relay.edn and is refused at the call.
- No approval before a move. relay#53 asked for one, and locked decision
  1 (no holds, no approvals) replaced that with exact undo.
- A call is checked whole before anything moves, and refused whole when
  any move is bad. A call whose moves touch the same path, or one inside
  another, is refused. Then the moves of a call never depend on each
  other's order, and undo can check every step against the disk on its
  own. Renaming a folder and filling it takes two calls.
- Moves use an atomic rename after a check that the target is absent.
  Java's plain move would copy and delete across disks, so a move to
  another disk is refused instead. The check and the rename are not one
  system call (macOS has `renamex_np` with `RENAME_EXCL`, which the JVM
  cannot reach). The gap between them is a race that needs precise
  timing, which the threat model excludes.
- relay never moves a symbolic link or a folder that holds one, nor
  anything that is not a file or folder. A moved link with a relative
  target would point somewhere else, possibly outside.
- A case-only rename (`Statement.PDF` to `statement.pdf`) is refused with
  a plain reason on a case-insensitive disk. The target exists, as the
  same file. The steward can rename through another name in two calls.
- Undo is the operator's only, from the CLI. It refuses, touching
  nothing, when a moved thing is gone or changed (by content, not by
  time), when something new is at an old place, or when a folder on
  either side is no longer itself (a link put in its place). A folder
  undo made that now holds something new is kept and named. If relay
  stops between the two events of a call, undo lists the moves for Kira
  to check by hand.
- A moved folder may hold at most 10,000 entries, so a fingerprint
  cannot take minutes.

Tests: `files_test`: the grant in relay.edn, folders that are or hold a
secret, load-config against the data directory, the source and target
decisions, a property that `batch-problems` finds exactly the pairs that
touch, then on real temp directories: a move and its undo, every refusal
moving and recording nothing, a folder moving whole, undo refusing after
an edit, a move by Kira, something new at the old place and a link swapped
in, a call relay never finished, who may move and undo, and a writable
folder that is a link to the data directory. I7 extended:
`undoing-every-call-restores-the-tree-byte-for-byte` builds a generated
tree with a link out of the folder, applies generated calls (sources
mostly picked from what is there), checks that nothing outside changed
and no file was lost, then undoes every call in reverse and compares the
whole tree. Removing the folder cleanup from undo makes it fail.

Deferred: undo from the client (`_relay/` protocol) waits for B11's
ready view, which lists moves with undo. A role cannot undo its own
moves.

Fix round 1. relay now walks a source folder only when its real path is
strictly inside a writable folder and holds none of them. Before this, a
move from any host folder walked it first and leaked one bit per walk.
A folder it cannot list, or a file it cannot read, is a refusal labelled
private ("it holds something relay cannot read"), not an exception. An
exception would reach the tool runner unlabelled, carrying a nested path.
Any other IOException while probing becomes a labelled refusal that names
only the call's own path. New tests: an unreadable folder inside and
outside the writable folder; a link swapped in two levels above a source;
an edit inside a moved folder; the labels on files/undone. The I7 property
now edits, adds or removes one file in what the last call moved. It checks
that undo then refuses and touches nothing, and puts the change back. The
three mutants the review reported each fail a test now.
