# B3: the steward's shell

A house role granted `:shell true` gets the `sh` tool, which runs a
command in a Linux container relay keeps for the data directory. The
output goes back to the role as the tool's result. `docs/house-shell.md`
describes the design with diagrams.

What was built:

- `relay.shell`: the settings check, the mount check, names derived
  from the data directory, every runner argument vector, the result
  text and labels, and the edges (start, stop, status, build, run one
  command). `resources/house/Containerfile` holds the image.
- relay.edn: a `:house` section (`:runner`, `:mounts`, `:image`,
  `:timeout-seconds`, `:output-limit`, `:cpus`, `:memory`) and a
  `:shell` grant. `:shell` is refused for a public role, without
  `:house`, and on a script harness. A remote MCP tool reaches a house
  role only as `read` or `edit`.
- `tools/manifest` refuses to build a house role's session with an
  egress tool, or a remote tool of another class, even when relay.edn
  validation was bypassed (O3).
- `relay house build|up|down|status`; the tick starts the shell before
  any wake, and so does the first `sh` call.

Judgment calls:

- `:runner` is only the program (`["container"]`, `["docker"]`,
  `["podman"]`), not an argument template. relay composes every
  option itself, so relay.edn cannot express a runner without
  `--network none`, a published port or a writable mount. The plan's
  "refuse a runner without `--network none`" becomes a property of the
  composed argv, plus a refusal of a runner that names a network. A
  full template would let Docker users add options, at the cost of a
  check on what they add; the structural version was chosen.
- Mounts appear at their own paths inside the container, so the
  steward's paths are Kira's paths (B9's moves need that). Each source
  is the real path, checked again when the container starts, with a
  `/System/Volumes/Data` firmlink prefix stripped and by file identity
  (fix round 1).
- Scratch is a tmpfs, and relay keeps the union of the labels of every
  session that ran a command since the container started, recorded
  before each command, in `<data>/shell/container.edn`. Every result
  carries them as they stood when the command started and again when it
  ended, plus `private` (fix round 1: a command overlapping a
  contaminated writer had carried only the first read). Without this, text from a stranger's
  mail could pass through `/scratch` to a clean session and a recipe
  change shaped by it would go unflagged (decision 14).
- The shell's own state is a file under the data directory, not log
  events: it describes a running container, which the log cannot know
  about after a reboot, and it is reset whenever the container is.
- `sh` is class `read`: it changes nothing outside the container.
- A failure to start the shell from the tick goes to the tick's stderr
  only. Telling Kira belongs with B4's messages.
- Containers run with `--init`, as user `steward` (uid 1000), with a
  read-only root, and `timeout -k 5 <limit>` inside the VM.

Tests: `shell_test.clj` (settings, mounts, argv and naming properties,
I1 over generated relay.edn, provenance through scratch, the life of the
container against a stand-in runner, the CLI and the tick) and
`shell_live_test.clj` (serial; builds the image, checks I7 by writing,
removing and moving files in a mount, checks the time limit inside the
VM, and runs the escape probe). The pentest `s18-shell-walls` runs the
same probe through `relay tool` as a hub that obeys an attacker. Both
remove exactly their own container and image by name.
