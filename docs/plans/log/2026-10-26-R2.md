# R2: fixes from Codex's adversarial review, round 2

Codex's follow-up round found two in-scope defects. Both let a
stranger's text end up somewhere the shell reads as Kira's own, so it
reached her with live links and the recipe changes it shaped went
unflagged.

## files_move into a trusted folder

A session that read a stranger's mail could move
`downloads/injected.txt` into a trusted `notes` mount. From then on,
every shell read of `notes` counted as Kira's own.

- `relay.files/trust-problem` (pure) refuses a move whose target is in
  a trusted mount, or would hold one, when its source is not inside a
  trusted mount. The session's labels play no part. The text the
  steward gets says the file would come from outside and that Kira can
  move it there herself.
- The target is compared the way the disk compares it: firmlinks
  removed, NFC, lower case. The edge also checks whether the target's
  nearest existing folder, or any folder above it, is the same file as
  a trusted mount (`same-file-mounts`), which covers links and other
  names. A source counts as inside a trusted folder only by its exact
  real path, so any doubt refuses the move. A trusted mount that does
  not exist yet still blocks targets by its name, so nothing can create
  it from outside. A moved folder is judged by its source.
- Moves within a trusted folder, out of one, between two trusted
  folders, and between untrusted places still go ahead. A file that has
  left a trusted folder counts as outside once it is out. `relay undo`
  can still put it back, because undo is Kira's and returns the file to
  where it was.
- The `files_move` description names the trusted folders, so the
  steward knows the rule before it tries a move.

Tests: `a-move-into-a-trusted-folder-must-come-from-one` (case, accents,
firmlinks, identity, a target that holds a mount, a mount that does
not exist yet); property
`a-move-into-a-trusted-folder-is-refused-exactly-when-it-comes-from-outside`;
`nothing-from-outside-moves-into-a-trusted-folder` on disk (clean and
contaminated sessions, a folder, another case, a link, undo); property
`nothing-from-outside-ever-lands-in-a-trusted-folder` over generated
trust layouts and moves, which checks by content that nothing ends up
in a trusted folder unless it started in one. Pentest
`s24-files-never-destroyed` now mounts its Shared folder as trusted,
tries four ways to file something there and expects each to be refused
as from outside. It also moves a file out of Shared and undoes that
move.

## Trusting a mount later

`record-session!` stored only the session's own labels, and mount trust
was not part of the container's spec. A file copied into scratch from
an untrusted mount became clean once Kira marked the mount trusted.

- Before each command, `sh!` records the full provenance in the scratch
  record: the session's labels plus the untrusted mounts' `contaminated`
  and `files:<name>`. Whatever the command writes to scratch carries
  those labels.
- `shell/spec` now takes the mounts and digests each one's trust along
  with the run argv. A trust change therefore replaces the container
  and its scratch.

Tests: `scratch-holds-what-an-untrusted-folder-could-have-put-there`
(it also runs with the folder trusted and the old container forced, so
the record by itself still protects the copy);
`trusting-a-folder-replaces-the-shell-and-its-scratch`; property
`trust-is-part-of-the-container-spec`.

Docs: the README's mounts and files_move paragraphs,
`docs/house-shell.md`, and the spec's StewardShell invariant and
MoveFiles rule.
